# Cursor vs. Claude Code for our development workflow — six-month assessment

**Author:** Maša Novak  
**Date:** April 2025  
**Audience:** Kvant engineering team, leadership  
**Status:** Final — shared for team discussion

---

## Why this document exists

We ran a semi-structured trial over roughly six months: some engineers primarily on Cursor, some primarily on Claude Code, most bouncing between both depending on the project and their mood. I took notes. This is my honest read on where things stand.

The short version is at the bottom if you just want the recommendation.

---

## What we actually tried

**Rok** used Cursor as his primary environment for most of the Iskratel MLOps scoping work and the earlier Krka document classification project. He is an IDE-native person — muscle memory in VS Code, prefers to stay in the editor. He ran Cursor Pro for the full six months.

**I** (Maša) spent the first three months defaulting to Cursor and switched to Claude Code as my primary around January after the Pipistrel onboarding prep work showed me a few things about agentic task execution I hadn't seen before. Still use Cursor occasionally for specific things.

**Jaka** tried Claude Code briefly in February, found the terminal-first interface annoying, went back to Cursor. He has the most consistent preference on the team and it is firmly Cursor.

**Andraž** doesn't have a strong view and uses whatever is suggested. Currently mostly Claude Code.

---

## Where each tool actually shone

### Cursor

**Multi-file refactors in a familiar codebase.** Cursor's Tab completion and Composer mode genuinely shine when you know the codebase well and want to make consistent changes across many files quickly. On the Krka RAG project, Rok used Composer to push a prompt-template refactor across about forty files in under an hour. That kind of change is tedious and error-prone manually. Cursor handled it well.

**Staying in flow inside an existing project.** If you are already in VS Code, Cursor is nearly zero overhead. You don't context-switch. Chat is there, completions are there, it all lives in the editor. For people like Jaka who are deeply editor-native, the friction of switching to a terminal-first tool is real and shouldn't be dismissed.

**Smaller, well-defined tasks with immediate feedback.** Writing a single function, fixing a specific bug, explaining a block of code. Cursor's inline interface makes this feel fast. The feedback loop is tight.

### Claude Code

**Longer agentic tasks where I want to hand something off.** The thing Claude Code does that Cursor does not is execute — it reads files, writes files, runs shell commands, checks the output, adjusts. On the Pipistrel scoping work I used it to build a document processing pipeline (DITA-ish XML, inconsistent schema) and it handled the whole loop: inspect samples, write parser, test against edge cases, fix. I ran it like a junior engineer on a defined task and came back to review. Cursor can do some of this with Composer but the agentic loop is shallower.

**Starting new projects from scratch.** No existing muscle memory to preserve. Claude Code's approach — work in the terminal, treat the filesystem as the interface — is actually well-suited to greenfield. You're not fighting an existing editor layout.

**Prompt and eval work.** Any time I am doing LLM-adjacent development — testing prompts, evaluating model outputs, iterating on system prompts — Claude Code's context window and conversational depth are noticeably better. This matters a lot for Kvant specifically given how much of our work is in this territory.

## Where each tool failed or frustrated

### Cursor

The context window and retrieval over large projects is inconsistent. On the Iskratel scoping work, Rok had several incidents where Cursor gave confident but wrong answers because it had failed to load a relevant file. The @ file mechanism helps but requires you to already know what to include, which somewhat defeats the purpose.

Cursor's model quality has also fluctuated. The periods when they default to weaker models or when claude-3-5-sonnet access is laggy are noticeable. We are, to some degree, paying for editor UX and then getting model access on top — the model layer is not fully in our control.

### Claude Code

The terminal interface is a real barrier for some people. This is not a small thing. Jaka's reaction is not irrational — if you have spent years with an IDE, a terminal-first tool feels like a regression, and productivity loss from interface friction is real even if the underlying model is better.

Context management across long sessions can get messy. Claude Code's /compact helps, but I've had sessions where the accumulated context produced confused outputs that required me to start fresh. Cursor's per-file scoping avoids some of this by limiting scope explicitly.

Cost is also a live concern. Claude Code subscriptions are currently $100/month per seat at the Pro level. Cursor Pro is $20/month. At current team size (four active users), that difference is €800+/year, which is not significant at Kvant's billing rates, but it's not zero.

## Productivity observations

I am skeptical of anyone who claims precise productivity percentages from AI coding tools. The variables are too many. What I can say:

For tasks where Claude Code excels — agentic, multi-step, LLM-adjacent — it is meaningfully faster than anything I've used before. The Pipistrel pipeline I mentioned would have taken me a full day manually; with Claude Code it was three hours including review.

For tasks where Cursor excels — familiar codebase, inline completion, small fixes — the gap between Cursor and Claude Code is small or Cursor wins on friction alone.

The biggest productivity gains come from matching tool to task, not from picking one tool and applying it everywhere.

## Recommendation

**Default to Claude Code for the engineers who are comfortable with it (currently me and Andraž). Keep Cursor available for Rok and Jaka — no mandate either direction.** 

Do not force adoption. The engineers who prefer Cursor are not wrong; they are working in the modality that matches their workflow. Forcing a terminal-first tool on someone who hates terminals will cost more in productivity than any model quality gain recovers.

What I would push for: when starting a new project from scratch, try Claude Code first. The greenfield case is where the interface friction matters least and the agentic depth matters most.

Revisit in six months. The gap between the tools is narrowing from both sides.
