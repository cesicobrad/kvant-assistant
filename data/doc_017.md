# Technical Report: Chroma vs. Qdrant vs. pgvector — Vector DB Evaluation for Client Deployments
**Author:** Žiga Potočnik
**Date:** 2023-08-14
**Audience:** Internal — Kvant engineering team
**Status:** Concluded — Qdrant adopted as default. Revisit if requirements change.

---

## Why We Did This

By mid-2023 we had used Chroma on two PoCs (Outfit7, one internal prototype) and were evaluating options before the Krka engagement (corpus ~4,000 documents, production requirements). Chroma was fast to set up but I had concerns about its production readiness. This report documents the evaluation we ran over three weeks in July–August 2023.

---

## Options Evaluated

| Database | Version tested | Hosting model | Cost |
|----------|---------------|---------------|------|
| Chroma | 0.4.5 | Self-hosted (Docker) | Open source |
| Qdrant | 1.4.0 | Self-hosted (Docker) | Open source |
| pgvector | 0.5.0 (Postgres 15) | Self-hosted | Open source |
| Weaviate | 1.21.0 | Self-hosted | Open source |

We did not evaluate Pinecone (managed-only, pricing model doesn't fit our client deployments) or Milvus (overhead too high for our scale). Weaviate was dropped after week 1 — the resource requirements were too high for the Hetzner instance sizes we typically provision and the configuration complexity wasn't justified for corpora under 50k documents.

---

## Test Corpus

- 4,200 documents, mixture of Slovenian and English regulatory text
- Chunk size: 400 tokens, 80-token overlap
- Embeddings: `text-embedding-3-large` (OpenAI), 3072 dimensions
- Total vectors: ~38,000

## Performance Results

### Retrieval Quality (RAGAS context precision on 50-question eval set)

| Database | Context Precision | Context Recall | Notes |
|----------|------------------|----------------|-------|
| Chroma | 0.71 | 0.74 | Acceptable; slightly worse on exact-match queries |
| Qdrant | 0.76 | 0.78 | Best overall; HNSW tuning helped |
| pgvector | 0.73 | 0.75 | Solid; exact kNN available (slower but higher recall) |

### Query Latency (p50 / p95, 50 concurrent users, top-k=6)

| Database | p50 latency | p95 latency | Notes |
|----------|-------------|-------------|-------|
| Chroma | 180ms | 620ms | p95 spikes under load |
| Qdrant | 95ms | 210ms | Consistent; HNSW approximate search |
| pgvector | 140ms | 380ms | Exact search; higher but predictable |

### Operational Characteristics

| Database | Persistent by default | Metadata filtering | Backup/restore | Production maturity |
|----------|-----------------------|--------------------|----------------|---------------------|
| Chroma | No (in-memory default) | Basic | Manual | Low |
| Qdrant | Yes | Rich (payload filtering) | Snapshot API | Medium-High |
| pgvector | Yes (Postgres) | Full SQL | Standard Postgres | High |

## Discussion

**Chroma** is excellent for prototyping. Setup is under 5 minutes. For PoCs and internal experiments it's the right tool. For production, it has two problems: the default in-memory mode has caused data loss in our experience (see Outfit7 notes), and the metadata filtering capabilities are limited compared to Qdrant. I do not recommend Chroma for anything client-facing. It's a dev tool.

**pgvector** is compelling if the client already runs Postgres (many do) and has simple querying needs. The operational simplicity of not adding a new database engine to a client's stack is real. Retrieval quality with exact kNN is marginally better than Qdrant's approximate search, though the latency penalty matters for interactive use. For the NLB engagement specifically, pgvector on their existing Postgres infrastructure was briefly considered and would have simplified the data residency discussion. We went with Qdrant because of the richer metadata filtering and the snapshot API for backups.

**Qdrant** wins on retrieval quality, latency, metadata filtering expressiveness, and the snapshot API. The HNSW parameter tuning requires more care than Chroma (see the Mercator post-mortem for what happens when you get it wrong), but the documentation is good and the defaults are reasonable for our corpus sizes. Qdrant is our default for production deployments.

---

## Recommendation

- **PoCs and internal prototypes:** Chroma (speed of setup wins)
- **Production, new infrastructure:** Qdrant
- **Production, client already on Postgres:** pgvector (seriously consider it — operational simplicity matters)

This recommendation is based on corpora in the 5k–100k vector range. For much larger corpora or high-concurrency requirements, revisit. Also revisit if Chroma releases a stable production-grade version — the API is nicer to work with.
