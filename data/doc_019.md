# Technical Report: Reranking Strategies — Evaluation for RAG Pipelines
**Author:** Žiga Potočnik
**Date:** 2024-04-29
**Audience:** Internal engineering
**Status:** Working document — update when we have more data

---

## Background

Reranking — applying a cross-encoder to re-score and reorder retrieved candidates before passing to the generation model — is frequently cited as a high-value improvement for RAG systems. The theory is sound: bi-encoder retrieval (our standard dense search) optimizes for approximate similarity at scale; cross-encoders can do full attention over query-document pairs but are too slow for first-stage retrieval. Using them for reranking a small candidate set (top-20 → top-6) gets the best of both.

We have talked about reranking in several proposals (Krka, NLB) and descoped it from Mercator Polica due to timeline pressure. This report documents an evaluation we ran in April 2024 to get real numbers.

---

## Evaluation Setup

- Corpus: Krka Phase 1 corpus (1,800 documents, ~22,000 chunks, Slovenian + English)
- Base retrieval: dense only, `text-embedding-3-large`, top-20 candidates
- Eval set: 80 questions (Krka golden dataset)
- Metrics: RAGAS context precision, context recall; also manual review of 20 questions
- Rerankers evaluated:

| Reranker | Type | Hosting | Cost |
|----------|------|---------|------|
| BGE Reranker v2-m3 | Cross-encoder | Self-hosted (CPU) | Compute only |
| Cohere Rerank v3 | API | Cohere API | €0.001/search unit |
| GPT-4o-mini as judge | LLM reranker | OpenAI API | ~€0.002/query |

---

## Results

### Retrieval Metrics (top-6 after reranking vs. baseline top-6)

| System | Context Precision | Context Recall | Latency added |
|--------|------------------|----------------|---------------|
| Baseline (no reranker) | 0.76 | 0.78 | — |
| + BGE Reranker v2-m3 (CPU) | 0.81 | 0.80 | +340ms p50 |
| + Cohere Rerank v3 | 0.83 | 0.81 | +180ms p50 |
| + GPT-4o-mini as judge | 0.79 | 0.77 | +1,100ms p50 |

### Manual Review Observations (20 questions)

BGE and Cohere rerankers both reliably improved results on Slovenian-language queries where the bi-encoder was surfacing English-language chunks over more relevant Slovenian ones. This is the most important finding — the embedding model has a slight bias toward English that the cross-encoder partially corrects.

GPT-4o-mini as a reranker was inconsistent. On straightforward factual queries it added latency without improving precision. On ambiguous queries it sometimes improved and sometimes hurt results, seemingly depending on how the reranking prompt was phrased. Not repeatable enough to trust.

---

## Cost Analysis

At 500 queries/day (typical client scale):

| Reranker | Monthly cost | Latency impact |
|----------|-------------|----------------|
| BGE (self-hosted, CPU) | €0 (existing infra) | +340ms |
| Cohere Rerank v3 | ~€15/month | +180ms |
| GPT-4o-mini as judge | ~€30/month | +1,100ms |

BGE self-hosted on the same Hetzner instance is essentially free and adds 340ms — acceptable for internal knowledge assistants where users are reading and thinking, less acceptable for customer-facing chatbots where latency is more visible.

Cohere Rerank v3 is surprisingly cheap at scale and has lower latency than BGE on CPU. If we add a GPU or Cohere's latency stays this good, it becomes the clear winner.

---

## Recommendation

**Add BGE Reranker v2-m3 as default for all new RAG deployments going forward.** The precision improvement (0.76 → 0.81) is significant, the cost is negligible on existing infrastructure, and the Slovenian-language correction effect is real and relevant for almost all our clients.

For Mercator Polica specifically: adding the reranker was in the August eval report recommendations (€1,800 estimated). Based on this evaluation I'd revise that estimate to 2 days of work (~€1,200). The improvement should address the context precision gap without touching the retrieval architecture.

Do not use LLM-as-judge reranking in production. It's a useful evaluation tool but the latency and cost don't make sense when a cross-encoder does better for almost nothing.
