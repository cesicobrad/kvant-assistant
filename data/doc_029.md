# Should we standardize on uv for Python project management?

**Author:** Rok Česen  
**Date:** March 2025  
**Audience:** Kvant engineering team

---

## The problem

We have been inconsistent about Python environment management for long enough that it's causing real friction. Currently:

- Some projects use `pip` + `venv` (most of the older ones)
- The Krka RAG project uses Poetry (my choice at the time, I stand by it for that project, but it has caused issues)
- A couple of experiments use neither, which is its own problem

The Iskratel MLOps scoping work forced this conversation because we need to agree on a stack before we start building anything for them. This is a good moment to make a decision and document it.

---

## Options considered

### pip + venv

The default. Everyone knows it. No learning curve, no extra tooling, no surprises when a new person joins.

**Problems:**

- No lockfile by default. `requirements.txt` is not a lockfile. I know we have `pip freeze` but we don't use it consistently and even when we do, the output is noisy and doesn't distinguish direct from transitive dependencies.
- Slow. Not "annoying slow" — genuinely slow in CI. On the Krka document classification project, our GitHub Actions environment setup was taking 4–5 minutes on a clean runner for a moderately complex dependency set. We got used to it. We shouldn't have.
- No dependency resolution worth speaking of. pip will happily install incompatible versions if you let it, and tell you about it only after the damage is done.

### Poetry

We used Poetry on the Krka RAG project and the experience was mixed. Dependency resolution is real and it saved us from at least two version conflicts I can think of. The `pyproject.toml` workflow is cleaner than `requirements.txt`. The lock file is genuinely a lock file.

**Problems:**

- Poetry's virtual environment behavior is idiosyncratic and has bitten us when running in Docker. We spent an afternoon on the Krka project debugging a container build that worked locally and failed in CI because of how Poetry handles venv paths in certain environments.
- Installation is slightly fussier than it should be. The recommended `curl | python` install method always makes me slightly uncomfortable in CI pipelines.
- Plugin ecosystem is immature for some of the things we do.
- Slow builds — not as bad as pip in the worst case, but Poetry's own install overhead adds up.

### uv

uv is a Rust-based Python package manager and resolver from Astral (the Ruff people). It is fast — genuinely, remarkably fast. Local benchmarks I ran last month on a clean environment showed uv resolving and installing a moderately sized dependency tree (similar to the Krka RAG requirements) in about 8 seconds. pip took about 2 minutes 20 seconds on the same machine.

It handles virtual environments, lock files, Python version management, and `pyproject.toml` workflows. The interface is largely pip-compatible (`uv pip install` does what you expect), which matters for onboarding.

**Concerns:**

- It is newer and less battle-tested than pip or Poetry. The Astral team moves fast and the changelog has had a few breaking changes in minor versions. That said, the project is well-maintained and the core functionality has been stable in our testing.
- Some third-party documentation and tooling still assumes pip or Poetry. This is a decreasing problem but it exists.

---

## The CI problem is the deciding factor

The Krka document classification CI was slow. We accepted it because the project was time-pressured and we didn't want to touch the environment setup mid-project. On the Iskratel MLOps work, if we build a proper training and evaluation pipeline, we will be running CI frequently — possibly many times a day during active development. A 4-minute environment setup per run is a real cost in iteration speed.

I ran uv in a test pipeline. Environment setup: **22 seconds** on a clean runner for a comparable dependency set. This is not a marginal improvement.

---

## Recommendation

**Adopt uv as the standard for new Python projects going forward.**

- New projects: start with `uv init`, use `uv.lock` for lockfiles, use `uv run` for execution
- Existing projects: migrate opportunistically, not urgently — do it when you're already touching the environment for another reason
- Poetry projects (i.e., Krka RAG): leave them as-is for now; the migration cost mid-engagement isn't worth it
- pip + venv projects: migrate the ones with active development on new sprints; archive the rest as-is

This is not a "rip everything out" call. It is a "don't start new things with the old tools" call.

For the Iskratel MLOps project specifically: start with uv from day one. The CI speed improvement alone justifies it, and we won't have legacy constraints to work around.
