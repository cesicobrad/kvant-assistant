# Post-Mortem: Production Outage — NLB Legal Assistant, September 2024
**Incident date:** September 4, 2024
**Duration:** 6 hours 14 minutes (09:17 – 15:31 CEST)
**Severity:** High — full service unavailability for 43 active users
**Author:** Matic Demšar
**Reviewed by:** Maša Vidmar, Tine Hribar
**Date written:** September 9, 2024
**Status:** Final

---

## Summary

The NLB Legal Assistant went fully offline for 6 hours and 14 minutes on September 4, 2024, due to an out-of-memory (OOM) crash on the Hetzner CX31 instance running the Qdrant vector database and FastAPI backend. Root cause was a combination of a runaway embedding reindex job triggered manually by Nika on the previous evening, an absence of memory limits on the Docker containers, and no alerting configured. The outage was discovered by the NLB team, not by us. This is the part that is most embarrassing and must not happen again.

## Root Causes

**Primary:** The Qdrant reindex job was run on an instance with insufficient memory. A full collection reindex loads the entire vector dataset into RAM alongside the existing serving process. The CX31 instance (16GB RAM) was adequate for serving but not for serving + reindexing simultaneously. This was not tested or documented.

**Contributing — no memory limits:** Docker containers had no memory limits configured. The OOM killer terminated Qdrant rather than the reindex job, leaving the API running in a broken state that returned errors instead of a clean failure.

**Contributing — no alerting:** Uptime monitoring was not configured. There was a note in the Matic's deployment checklist that said "TODO: set up UptimeRobot or equivalent" dated June 2024. It was never done. We discovered the outage from the client, not from our own systems.

**Contributing — no documented procedure for incremental updates:** The reindex was triggered manually because there was no incremental update pipeline. New documents should never require a full collection reindex. This is a design gap.

---

## What We Did Right

Not much in this incident. The snapshot restore worked correctly and was faster than expected (25 minutes to restore vs. the ~2 hours a full reindex would have taken). The decision to restore from snapshot rather than attempt to resume the broken reindex job was correct.

---

## What We Got Wrong

1. Running a full reindex on a production instance with no memory ceiling and no off-hours maintenance window
2. No uptime monitoring on any client-facing system (this was known and deprioritized — that ends now)
3. No incremental document update path — adding 47 documents should not touch the full index
4. Discovering the outage from the client rather than our own tooling
5. The CX31 sizing was based on serving load only; operational tasks were not considered in the original sizing

---

## Remediation (Completed)

- Qdrant instance upgraded to CX41 (32GB RAM) — cost delta: +€18/month, NLB informed and accepted
- Memory limits added to all Docker containers (Qdrant: 20GB hard limit, FastAPI: 2GB)
- UptimeRobot monitoring configured for NLB and all other active client deployments (should have been day 1)
- Incremental document update pipeline added to backlog as P0 — Nika to implement by end of September
- Deployment checklist revised: uptime monitoring is now a go-live blocker, not a TODO

## Impact on Client Relationship

Petra Kobal was professionally unhappy. Damjan Repič sent a formal email requesting a written explanation, which Anja provided. The SLA in the contract specifies 99% uptime, which we breached (6h14m outage in a 30-day month = 99.13% — technically compliant but barely and only because the SLA is measured monthly). Damjan noted this in writing. We offered one month of extended support at no charge; Petra accepted.

The relationship is intact but the trust buffer is thinner. Matic must not touch production infrastructure on a Friday afternoon or evening without explicit sign-off. This is now a team rule, not a guideline.
