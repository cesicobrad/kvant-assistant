# Why we stopped using LangChain agents (for now)

*Žiga Potočnik — 2024-06-18*

---

Short version: LangChain agents are not reliable enough for client-facing production systems, and the abstraction cost is too high when things go wrong.

Longer version.

We used LangChain agents on two projects — Pipistrel's maintenance doc assistant and an internal prototype for Krka's regulatory query tool. In both cases we hit the same failure pattern: the agent works fine in the happy path, then does something completely inexplicable the moment a query falls slightly outside the training distribution. With Pipistrel, the agent started looping on tool calls when a document returned a partial result — three rounds of the same retrieval, same empty response, before we caught it. No error, no timeout, just burning tokens in a circle. We had to add external watchdog logic that should not have been necessary.

With Krka it was worse because the stakes are higher. The agent occasionally decided to skip retrieval entirely and answer from parametric memory, which is exactly the failure mode you cannot have in a regulatory context. Tracing it in LangSmith helped us see it happening, but not reliably reproduce it or fix it at the framework level. The tool-calling logic is too opaque. When you need to explain to a client why the system did something, "the agent decided" is not an answer.

The abstraction also made debugging slow. Error messages that bubble up from inside LangChain chains are often useless — they tell you something failed three layers down without enough context to act on. Rok spent a full day on a version conflict between LangChain and LlamaIndex on the Pipistrel deployment that would have taken two hours if we'd been closer to the metal.

We are not saying LangChain is bad. The document loaders are fine, some of the utility stuff is useful. But agents specifically: no.

What we're doing instead: explicit orchestration, written by us. Basically a state machine or a simple loop with conditional branches, direct API calls to GPT-4o or Claude Sonnet 4.5, retrieval via Qdrant client directly. More code, but every line is ours and we know what it does. Evals with RAGAS run against each step separately. Slower to build once, faster to debug forever.

We'll revisit if the framework matures. For now: write the logic yourself.
